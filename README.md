# Lulz 1.0.1

**Зелёная консоль для проверки веб-конфигурации, локальных исходников и зависимостей.**

Lulz объединяет меню, проверку URL, анализ сохранённых HTTP-сессий, локальных исходников, инфраструктурных конфигураций и зависимостей.
Результаты сохраняются в JSON, HTML, Markdown и SARIF 2.1.0; доступны baseline и пороги для CI.
Исходный код поставляется вместе с программой под лицензией MIT.
Программа работает на Python 3.11+ и использует только стандартную библиотеку: устанавливать пакеты через pip не нужно.
Версия 1.0.1 содержит 64 фиксированных правила и семейство правил OSV для найденных бюллетеней; актуальный каталог выводит `python lulz.py rules`.

## Быстрый запуск

### Windows

1. Открой папку `Lulz`.
2. Дважды нажми **Start-Lulz.cmd**.
3. Выбери действие в меню и введи URL либо путь к проекту.

Лаунчер включает зелёный текст, UTF-8 и ищет `python`, затем `py -3`.
Если Python отсутствует, установи Python 3.11+ с [python.org](https://www.python.org/downloads/).
Запуск из PowerShell в папке программы:

```powershell
python .\lulz.py
```

### Linux / macOS

```bash
python3 lulz.py
```

Также доступен `sh start-lulz.sh`. Для запуска установленного пакета предусмотрен `python -m lulz`.
В примерах ниже используется `python`; при необходимости замени его на `python3`.

## Главное меню

| Пункт | Действие |
|---|---|
| 1 | Ввести URL и выбрать все веб-проверки либо отдельные модули |
| 2 | Выбрать файл/каталог и проверить исходники на SQLi/XSS и другие риски |
| 3 | Прочитать зависимости; при выборе онлайн-режима сопоставить версии с OSV |
| 4 | Посмотреть последние сохранённые отчёты |
| 5 | Сравнить два JSON-отчёта Lulz |
| 6 | Прочитать справку об охвате |
| 7 | Проанализировать сохранённый HAR-файл, при необходимости отфильтровав один хост |
| 8 | Проверить локальную конфигурацию и кандидаты на секреты |
| 9 | Объединить исходники, конфигурацию, секреты и зависимости в одном аудите проекта |
| 0 | Закрыть программу |

В выборе модулей `Enter` или `A` запускает все доступные проверки выбранного режима.
Для отдельных проверок введи номера через запятую; `0` возвращает назад.
Пути с пробелами можно вставлять в кавычках. Цвет отключается флагом `--no-color` или переменной `NO_COLOR`.

## Проверка URL

| Модуль | Что анализируется |
|---|---|
| `headers` | Заголовки защиты, CSP, HSTS, MIME sniffing, защита от встраивания, наблюдаемые CORS-настройки |
| `cookies` | Атрибуты Secure, HttpOnly, SameSite, требования префиксов cookies и совместимость атрибутов |
| `tls` | Обычное TLS-соединение, проверка сертификата, срок действия и согласованный протокол |
| `html` | Формы, передача данных по HTTP, mixed content и атрибуты внешних ресурсов |
| `disclosure` | Видимые в полученном ответе признаки раскрытия технической информации |

Веб-режим делает обычный GET указанного URL и следует не более чем трём перенаправлениям.
Переходы ограничены тем же origin; разрешено повышение с HTTP:80 на HTTPS:443 того же хоста.
Переход на другой origin или понижение HTTPS до HTTP останавливает цепочку и отмечает неполный результат.
Для режима только `tls` HTTP GET не выполняется; указывай адрес с `https://`.

Lulz не обходит ссылки, не загружает внешние ресурсы, не исполняет JavaScript и не отправляет формы.
В нём нет атакующих SQLi/XSS-запросов, перебора путей, проверки паролей или эксплуатации.
Это ограниченная проверка полученного ответа: динамическое поведение браузера и серверная логика ей не видны.
Отсутствие CSP само по себе не объявляется XSS, а отсутствие скрытого поля формы — подтверждённым CSRF.

```bash
python lulz.py web https://example.com --checks all
python lulz.py web https://example.com --checks headers,cookies,html
python lulz.py web https://example.com --checks tls --timeout 10
```

## Сохранённая сессия сайта: HAR

HAR-режим применяет веб-правила к ответам, уже записанным браузером, и позволяет охватить несколько страниц и API-ответов.
Поддерживаются `headers`, `cookies`, `html` и `disclosure`; доступен фильтр точного имени хоста.
HTTP-запросы не повторяются, адреса из архива не загружаются, содержимое страницы не исполняется.
TLS-сертификат по HAR не проверяется: для этого используется отдельный режим `web --checks tls`.

```bash
python lulz.py har ./session.har --host example.com --checks all
python lulz.py har ./session.har --profile quick
```

В `--host` указывается имя без схемы, пути, порта и wildcard; `example.com` не включает поддомены автоматически.
Отсутствующее в HAR тело ответа означает пропуск проверок тела; оно не считается пустой безопасной страницей.
Поддерживаются текстовые и base64-представления тел с ограничением размера.
Содержимое HAR, request headers, данные форм и значения cookies не отправляются во внешние сервисы.
Сам исходный HAR может содержать чувствительные данные; в отчёт попадают только ограниченные наблюдения и URL со скрытыми значениями query.

## Локальная конфигурация и секреты

```powershell
python .\lulz.py local "C:\Projects\site" --checks config,secrets
python .\lulz.py local "C:\Projects\site\.env" --checks secrets
python .\lulz.py local "C:\Projects\site\Dockerfile" --checks config
```

| Область | Что проверяется |
|---|---|
| Секреты | Блоки PEM private key, строковые литералы в полях учётных данных с порогом длины/энтропии, URL со встроенным паролем |
| Dockerfile | Пользователь финальной стадии с учётом локального наследования, отсутствие явного USER как отдельное замечание, удалённый ADD без checksum |
| Kubernetes JSON | Pod и шаблоны workload: privileged, host namespaces, hostPath, UID 0, runAsNonRoot, allowPrivilegeEscalation, широкие capabilities |
| Terraform JSON | Широкий ingress AWS security group, публичная адресация БД, широкие S3 ACL, отключённые ограничения Block Public Access, IMDSv2 optional |

Секреты не проверяются онлайн. Их значения, части значений и URL с паролем полностью скрываются в находках.
Эвристика не обнаруживает все виды секретов и может выделить тестовое значение; это кандидат для ручной проверки.
Приватные ключи распознаются по структуре PEM, без проверки криптографической корректности.

Kubernetes-правила учитывают наследование Pod securityContext и переопределения контейнеров; Linux-правила UID пропускаются для Windows Pod.
Отсутствие `runAsNonRoot` или `USER` не выдаётся за доказательство запуска от root.
Terraform оценивается по статическим значениям `.tf.json`; выражения и связи между ресурсами не вычисляются.
Наличие широкой ACL не доказывает фактическую публичность S3: блокирующие политики отдельно не вычисляются.
Структурные проверки Kubernetes/Compose YAML и Terraform HCL `.tf` не поддерживаются; распознанные такие файлы отмечают неполноту охвата.

## Общий аудит проекта

Режим `project` принимает папку и объединяет независимые разделы в одном отчёте.
Доступные разделы: `source`, `config`, `secrets`, `dependencies`.
Ошибки и ограничения каждого раздела сохраняются в общей сводке и в `metadata.components`.

```powershell
python .\lulz.py project "C:\Projects\site" --profile full --online
python .\lulz.py project "C:\Projects\site" --profile quick
python .\lulz.py project "C:\Projects\site" --checks source,secrets
```

`full` выбирает все разделы; `quick` исключает зависимости и использует локальные проверки.
Без `--online` выбранный раздел зависимостей строит только инвентаризацию.
Отсутствие поддерживаемых файлов или манифестов отображается как пропущенный раздел; ошибки и реальные ограничения не скрываются.

## SQLi, XSS и другие риски в исходниках

Для этой проверки нужен локальный файл или каталог проекта. Исходники читаются как данные и не выполняются.
Поддерживаются Python, JavaScript/TypeScript, PHP, HTML и распространённые шаблоны.

| Модуль | Основные правила |
|---|---|
| `sql` | Динамически собранный SQL перед API выполнения; интерполяция, конкатенация и форматирование |
| `xss` | HTML-синки, отключение экранирования, `mark_safe`, динамический `Markup`, небезопасные шаблонные контексты |
| `code` | Динамические eval/exec, shell-команды, pickle/dill, YAML-загрузчики, динамические шаблоны |
| `config` | DEBUG, запуск сервера с debug, отключение проверки сертификатов |

Python проверяется через AST с ограниченным отслеживанием строк внутри области видимости.
Правила JavaScript/PHP и шаблонов — лексические эвристики, преимущественно в пределах одной строки.
Это не полный межпроцедурный анализ: возможны пропуски и ложные срабатывания.
Находка содержит файл, строку, правило, CWE и рекомендацию; она требует проверки происхождения данных.
Параметризованный SQL и обычный автоматически экранируемый вывод не считаются уязвимыми сами по себе.

```powershell
python .\lulz.py source "C:\Projects\site" --checks sql,xss
python .\lulz.py source "C:\Projects\site\app.py" --checks all
```

```bash
python lulz.py source ./my-project --checks code,config --output ./audit-reports
```

## Зависимости и настоящие CVE

Поддерживаются точные версии пакетов пяти экосистем:

| Экосистема | Форматы |
|---|---|
| PyPI | `requirements*.txt`, `Pipfile.lock`, `poetry.lock`, `uv.lock` |
| npm | `package-lock.json`, `npm-shrinkwrap.json` |
| Packagist | `composer.lock`, включая packages-dev |
| crates.io | `Cargo.lock` для поддерживаемого публичного registry |
| Go | `go.sum` с точными версиями |
| Все пять | CycloneDX JSON SBOM с простыми package URL и точными версиями |

Можно указать конкретный файл. При выборе каталога рассматриваются подходящие файлы непосредственно в нём:
перечисленные lock-файлы, `requirements*.txt`, `bom.json` и `*.cdx.json`; рекурсивный поиск манифестов не выполняется.
Диапазоны версий не угадываются. Неподдерживаемые записи отмечаются как пропущенные.
Маркеры окружения requirements не вычисляются; условные зависимости включаются в инвентаризацию.
Для Poetry/uv/Pipfile и Cargo проверяется доступная информация о registry и источнике; распознанные неподдерживаемые VCS/direct/private-источники пропускаются.
Composer, requirements и npm сопоставляются по объявленному имени и версии; принадлежность конкретной сборки публичному пакету и происхождение private fork этим не устанавливаются.
CycloneDX PURL с qualifiers или subpath пропускаются как неподдерживаемая идентичность; qualifiers не отбрасываются для принудительного совпадения.
Локальные workspace-пакеты Cargo и editable/virtual/directory-пакеты uv не отправляются на поиск в OSV.
`go.sum` может содержать неиспользуемые версии: это инвентарь контрольных сумм, а не точный граф сборки; записи только `/go.mod` пропускаются.

Без `--online` создаётся **только инвентаризация**, без запросов к базе уязвимостей.
С `--online` Lulz обращается к [OSV API](https://google.github.io/osv.dev/post-v1-query/).
В теле запросов передаются имя, экосистема и точная версия пакета, а при пагинации — токен следующей страницы.
Исходные файлы проекта и их содержимое в OSV не отправляются.

```bash
python lulz.py deps ./my-project
python lulz.py deps ./my-project/package-lock.json --online
python lulz.py deps ./my-project/bom.json --online --timeout 15
python lulz.py deps ./my-project/Cargo.lock --online
python lulz.py deps ./my-project/composer.lock --online
```

**CWE** обозначает класс ошибки: например, CWE-89 для SQL injection и CWE-79 для XSS.
**CVE** — идентификатор опубликованной уязвимости; он выводится только если присутствует в записи OSV.
Если запись имеет лишь GHSA или другой идентификатор, Lulz не придумывает для неё CVE.
Версии из HTTP-баннеров не используются для присвоения CVE.
Совпадение зависимости с бюллетенем не доказывает происхождение установленного артефакта, его наличие на сайте, достижимость уязвимого кода или эксплуатацию.

## Отчёты и интерпретация

После проверки создаётся отдельная папка внутри `reports` рядом с программой:

- `report.html` — автономный отчёт с локальными фильтрами по уровню, категории, baseline и поиском по тексту;
- `report.json` — полный структурированный результат со схемой `1.0`, метаданными и охватом;
- `report.md` — текст для просмотра и включения в рабочую документацию;
- `report.sarif` — SARIF 2.1.0 для совместимых средств анализа и просмотра результатов.

Папку вывода можно изменить через `--output`. Существующие результаты не перезаписываются.
В находках указаны важность, уверенность, расположение, наблюдение, рекомендация и ссылки на источники.
Статус `observed` означает наблюдаемую настройку, `review` — кандидата для ручной проверки,
`advisory_match` — совпадение версии с опубликованным бюллетенем.

Значения cookies и параметров URL скрываются; исходные строки кода не копируются в находки.
Отчёты всё равно содержат имена файлов, пути, хосты и сведения о зависимостях: учитывай это при передаче.
HTML экранирует внешний текст; его собственный фиксированный JavaScript управляет фильтрами и не исполняет содержимое проверенной страницы.
Отчёт не загружает внешние скрипты или стили; фильтры также не отправляют данные в сеть.
SARIF сохраняет идентификаторы правил, доступное расположение, fingerprints и параметры находок; для локальных файлов используются файловые расположения, для веб-наблюдений сохраняется их URL-контекст.
Пустой список находок означает лишь отсутствие срабатываний в выполненных проверках.
Ошибки сети, пропуски, превышение лимитов и неполнота доступны в отчёте и не превращаются в заключение «безопасно».

## История и сравнение

```bash
python lulz.py history
python lulz.py history --output ./audit-reports
python lulz.py diff ./reports/BEFORE/report.json ./reports/AFTER/report.json
```

В последнем примере замени `BEFORE` и `AFTER` на реальные папки отчётов.
Сравниваются одинаковые типы проверки, цели и наборы модулей.
Для зависимостей также должен совпадать охват онлайн/офлайн и факт выполнения поиска бюллетеней.
Сравнение основано на правиле, расположении и доказательстве; оно показывает новые и больше не наблюдаемые находки.
Исчезновение находки, особенно при неполном отчёте, само по себе не доказывает исправление.

## Baseline и новые находки в CI

`--baseline` помечает текущие находки как `new`, `unchanged` или `updated`, сохраняя все находки и доказательства.
Нужны два завершённых отчёта совместимого охвата: цель, режим, модули и существенные параметры проверки должны совпадать.
Неполный предыдущий или текущий результат не применяется как baseline.
Офлайн-инвентаризация не может заменить онлайн-проверку CVE; аналогично учитывается фильтр хоста HAR.

```bash
python lulz.py source ./my-project --checks sql,xss --output ./audit-reports
python lulz.py source ./my-project --checks sql,xss --baseline ./audit-reports/BASELINE/report.json --new-only --fail-on medium --no-color
```

Замени `BASELINE` на папку первого завершённого отчёта.
`--new-only` меняет только применение порога `--fail-on`: CI учитывает новые и изменившиеся находки, а отчёт по-прежнему содержит все.
Без `--baseline` флаг `--new-only` отклоняется. Без `--fail-on` этот флаг не создаёт отдельного порога завершения.
Совпадение определяется правилом, расположением и доказательством; изменение расположения может появиться как новая находка.

## Автоматизация и коды завершения

```bash
python lulz.py --help
python lulz.py modules
python lulz.py rules
python lulz.py source ./my-project --checks sql,xss --fail-on medium --no-color
```

`--checks` выбирает модули явно. Вместо него доступен `--profile quick|full`; эти параметры взаимоисключающие.

| Режим | Профиль quick | Профиль full |
|---|---|---|
| `web`, `har` | headers, cookies | Все доступные модули этого режима |
| `source` | sql, xss | sql, xss, code, config |
| `local` | config, secrets | config, secrets |
| `project` | source, config, secrets | source, config, secrets, dependencies |

В `deps` выбор профилей не требуется: доступны инвентаризация и `--online`.

| Код | Значение |
|---|---|
| `0` | Команда завершилась; заданный порог находок не сработал |
| `1` | Ошибка выполнения или неполная проверка; подробнее в выводе и отчёте |
| `2` | Сработал `--fail-on`, либо неверен синтаксис аргументов CLI |
| `130` | Проверка в режиме CLI остановлена через Ctrl+C |

Порядок уровней: `critical`, `high`, `medium`, `low`, `info`.
`--fail-on medium` учитывает medium и более высокие уровни; без флага находки сами по себе не дают ненулевой код.
Ошибка или неполнота имеет приоритет над порогом. В интерактивном меню Ctrl+C возвращает управление меню.

## Пределы и охват

| Область | Встроенные пределы |
|---|---|
| URL | До 1 MiB тела; до 3 редиректов; до 12 000 HTML-элементов |
| Сеть URL | Тайм-аут 10 с по умолчанию, CLI 1–30 с; бюджет получения ответа до 60 с |
| HAR | Файл до 25 MiB, до 500 записей, до 1 MiB на тело и 16 MiB тел суммарно, до 5000 находок |
| Исходники | 1500 файлов, 512 KiB на файл, бюджет 32 MiB, 20 000 объектов обхода, 3000 находок |
| Парсинг исходников | До 100 000 узлов AST; лексические строки длиннее 8192 символов пропускаются |
| Конфигурация/секреты | 1500 файлов, 512 KiB на файл, 32 MiB суммарно, 20 000 объектов обхода, 2500 находок |
| Парсинг конфигурации | До 50 000 JSON-узлов; секреты в строках длиннее 65 536 символов пропускаются |
| Зависимости | До 20 манифестов по 5 MiB, до 200 уникальных пакетов |
| OSV | Бюджет 90 с, до 10 страниц на пакет, до 4 MiB на ответ |
| Импорт отчёта | JSON до 20 MiB |

Ссылки и junction при обходе исходников пропускаются, как и `.git`, `node_modules`, virtualenv, build/dist, reports и `.lulz-backups`.
TLS-проверка отражает одно обычное согласование с сервером; полный перебор протоколов и шифров не выполняется.
Сжатый HTTP-ответ вопреки `Accept-Encoding: identity` не распаковывается и помечается неполным для анализа HTML.

## Разработка

`lulz/cli.py` — меню и CLI; `web.py`, `har.py`, `source.py`, `project_checks.py`, `dependencies.py` — проверяющие модули;
`project.py` объединяет разделы, `models.py` задаёт схему результатов, `reports.py` экспортирует отчёты,
`baseline.py` сравнивает с базовым результатом, `catalog.py` строит каталог правил, `tests/` содержит тесты.
Проверки не требуют сторонних пакетов; тесты не отправляют атакующие запросы.

```bash
python -m unittest discover -s tests -v
```
